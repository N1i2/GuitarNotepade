## Раздел A. Общие вопросы о проекте

| № | Вопрос | Краткий ответ |
|---|--------|---------------|
| A1 | Что представляет собой ваш проект? | Веб-приложение «Guitar Notepad» для хранения, просмотра и редактирования гитарных песен: аккорды, паттерны боя, структура песни по сегментам, альбомы, подписки, отзывы и уведомления. |
| A2 | Какая практическая значимость проекта? | Упрощает музыкантам ведение личной библиотеки разборов, совместное использование материалов и организацию репертуара в одном месте вместо разрозненных файлов и заметок. |
| A3 | Кто целевая аудитория? | Гитаристы-любители и продвинутые пользователи, преподаватели, авторы разборов; администраторы платформы для модерации. |
| A4 | В чём новизна по сравнению с блокнотом или PDF? | Структурированное хранение (сегменты, аккорды, паттерны), поиск, роли, подписки на альбомы, социальные функции (комментарии, отзывы), единая платформа. |
| A5 | Это коммерческий продукт или учебный? | Учебный дипломный проект с архитектурой, пригодной для дальнейшего развития; платёжный модуль сейчас демонстрационный. |
| A6 | Какие основные функции реализованы? | Регистрация/вход, CRUD песен/аккордов/паттернов/альбомов, редактор структуры песни, аудио, профиль, подписки, уведомления, premium (заглушка), админ-функции. |
| A7 | Какие функции сознательно не реализованы? | Реальная оплата, полноценная проверка орфографии текстов песен, мобильное нативное приложение, офлайн-режим, продвинутый real-time чат. |
| A8 | Почему выбрана именно тема гитарного блокнота? | Личная потребность и узнаваемая предметная область; хорошо демонстрирует fullstack, работу с медиа, ролями и сложной доменной моделью. |
| A9 | Какой стек технологий использован? | Backend: ASP.NET Core, EF Core, PostgreSQL, MediatR. Frontend: Next.js, React, TypeScript, Tailwind. Инфраструктура: Docker, WebDAV (Яндекс.Диск). |
| A10 | Почему клиент-серверная архитектура, а не desktop? | Веб даёт кроссплатформенность, централизованное хранение, совместный доступ к контенту и проще масштабирование без установки ПО. |
| A11 | Сколько слоёв в системе? | Логически: клиент (браузер) → frontend → backend API → БД и внешнее хранилище файлов. В backend — Domain, Application, Infrastructure, Presentation. |
| A12 | Какие роли пользователей есть? | Guest (неавторизованный), User, Premium, Admin — с разным доступом к просмотру и созданию контента. |
| A13 | Чем Premium отличается от обычного User? | Сняты или расширены лимиты на создание контента, доступ к альбомам и расширенным возможностям (по бизнес-правилам домена). |
| A14 | Что может делать гость? | Просматривать публичные списки и детали песен, аккордов, паттернов; регистрироваться и входить; не создаёт и не изменяет контент. |
| A15 | Как измеряется успешность проекта? | Работоспособность ключевых сценариев, целостность архитектуры, соответствие ТЗ диплома, возможность демонстрации на защите. |
| A16 | Какие аналоги существуют? | Ultimate Guitar, Songsterr, личные заметки, Google Docs, специализированные табулатурные редакторы — у каждого свой фокус. |
| A17 | Чем ваш проект отличается от Ultimate Guitar? | Фокус на **личной библиотеке и собственных разборах**, а не на коммерческом каталоге чужих табулатур; гибкая структура сегментов и интеграция аккордов/паттернов пользователя. |
| A18 | Почему не мобильное приложение? | Для диплома веб-версия быстрее в разработке и демонстрации; интерфейс адаптивен, при необходимости возможен PWA или отдельное приложение позже. |
| A19 | Какой объём данных проект рассчитан обслуживать? | Архитектура ориентирована на рост данных: пагинация, индексы в БД, планируемая оптимизация запросов под большие библиотеки. |
| A20 | Есть ли ограничения дипломной версии? | Демо-оплата, не все security-улучшения внедрены, тестовое покрытие в процессе, i18n частично в плане доработок. |

## Раздел B. Архитектура и проектирование

| № | Вопрос | Краткий ответ |
|---|--------|---------------|
| B1 | Какую архитектурную модель использует backend? | Clean Architecture / слоистая: Domain → Application → Infrastructure → Presentation. |
| B2 | Зачем разделение на слои? | Изоляция бизнес-логики от БД и HTTP, тестируемость, независимость домена от фреймворков. |
| B3 | Что такое CQRS в вашем проекте? | Команды (изменение данных) и запросы (чтение) разделены через MediatR и отдельные handlers. |
| B4 | Зачем MediatR? | Уменьшает «толстые» контроллеры, единая точка входа в use-case, проще добавлять валидацию и логирование. |
| B5 | Что такое Repository pattern? | Абстракция доступа к данным; домен не знает деталей EF Core. |
| B6 | Зачем Unit of Work? | Координация транзакций и единая точка `SaveChanges` для связанных операций. |
| B7 | Почему DTO, а не сущности напрямую в API? | Скрытие внутренней модели, контроль контракта, защита от over-posting и утечки полей. |
| B8 | Где бизнес-правила? | В Domain (сущности, лимиты, роли) и в Application handlers (оркестрация сценариев). |
| B9 | Почему Next.js App Router? | Современный роутинг React, layout-композиция, возможность SSR/SSG для публичных страниц. |
| B10 | Как frontend общается с backend? | REST API через сервисный слой `lib/api/*`, JWT в заголовках (планируется httpOnly cookie). |
| B11 | Почему не GraphQL? | REST проще для диплома, Swagger документирует контракт, достаточно для текущих сценариев. |
| B12 | Есть ли микросервисы? | Нет, монолитный backend — оправдан для масштаба диплома и проще в сопровождении. |
| B13 | Как обеспечивается слабая связанность? | Интерфейсы в Domain, DI в Infrastructure/Presentation, handlers не зависят от контроллеров. |
| B14 | Что будет при смене БД? | Меняется Infrastructure (EF provider, миграции); Domain и Application остаются стабильными. |
| B15 | Почему PostgreSQL? | Надёжная open-source СУБД, JSON при необходимости, full-text, хорошая поддержка в EF Core. |
| B16 | Как хранятся файлы (аудио, аватары)? | Внешнее хранилище через WebDAV (Яндекс.Диск), в БД — метаданные и ссылки. |
| B17 | Почему файлы не в БД? | Большие бинарники нагружают БД и бэкапы; object storage/WebDAV — стандартная практика. |
| B18 | Как описана архитектура в документации? | Диаграммы в `Docs/Graph` (архитектура, Use Case, БД, последовательности, блок-схемы). |
| B19 | Соответствует ли код диаграммам? | В целом да по слоям и сущностям; отдельные диаграммы могут отставать от новых сущностей (reviews, subscriptions). |
| B20 | Какие паттерны на frontend? | Provider (auth, theme), context для редактора песни, сервисный слой API, компонентный UI-kit. |

## Раздел C. Backend (детально)

| № | Вопрос | Краткий ответ |
|---|--------|---------------|
| C1 | На какой версии .NET backend? | .NET 10 (`net10.0`). |
| C2 | Какие проекты в solution? | Domain, Application, Infrastructure, Presentation, Tests. |
| C3 | Как устроена аутентификация? | JWT Bearer: login/register выдают токен с claims (user id, role). |
| C4 | Как устроена авторизация? | `[Authorize]`, политика Admin, проверки владельца ресурса в handlers. |
| C5 | Сколько времени живёт JWT? | Настраивается в конфигурации (план: access ~15 мин + refresh token). |
| C6 | Как хешируются пароли сейчас? | Используется кастомный подход; в плане — переход на BCrypt/Argon2id. |
| C7 | Какие контроллеры есть? | Auth, User, UserManagement, Songs, Albums, Chords, StrummingPatterns, Reviews, Subscriptions, Notifications, Payments, Files. |
| C8 | Какие сущности в домене? | User, Song, SongStructure, Segment, Chord, StrummingPattern, Album, SongAlbum, Subscription, Notification, SongReview, SongComment и др. |
| C9 | Как устроена песня? | Метаданные + структура из сегментов с позициями, привязка аккордов и паттернов, опционально аудио. |
| C10 | Что такое сегмент песни? | Фрагмент текста/партии с привязанным аккордом и паттерном боя для отображения в таблице-редакторе. |
| C11 | Как работают подписки? | Пользователь подписывается на **альбом**; при изменениях — уведомления подписчикам. |
| C12 | Есть ли лимиты для free-пользователей? | Да, на количество песен, аккордов, паттернов; альбомы — для Premium/Admin. |
| C13 | Как работает premium? | Endpoint upgrade с демо-подтверждением оплаты; роль/флаги пользователя обновляются в домене. |
| C14 | Как работают уведомления? | Хранение в БД, список/unread count, отметка прочитанным; на frontend — polling. |
| C15 | Как обрабатываются ошибки API? | Exception filter + локальные ответы; цель — единый формат `code/message/details/requestId`. |
| C16 | Есть ли Swagger? | Да, подключается в `Program.cs` для документирования и ручного тестирования API. |
| C17 | Как применяются миграции? | EF Core migrations; при старте приложения — auto-migrate (план: ограничить для non-Development). |
| C18 | Как валидируются входные данные? | FluentValidation в pipeline Application + проверки в домене. |
| C19 | Зачем AutoMapper? | Маппинг Entity ↔ DTO без ручного кода в каждом handler. |
| C20 | Как реализован поиск песен/альбомов? | Фильтры + пагинация; поиск по строковым полям (план: индексы/full-text при росте данных). |
| C21 | Публичные vs приватные песни? | `IsPublic`; приватные доступны владельцу и админу. |
| C22 | Как загружается аудио? | Через API → WebDAV; лимиты размера на уровне Kestrel/FormOptions (~100 MB). |
| C23 | Как отдаются статические файлы пользователя? | FilesController для аватаров и дефолтных ресурсов; медиа — через URL из WebDAV. |
| C24 | Есть ли фоновые задачи? | Да, например cleanup уведомлений (background service в Infrastructure). |
| C25 | Как настроен CORS? | Для локальной разработки (frontend origin); production-политика настраивается отдельно. |
| C26 | Где конфигурация секретов? | `.env` / `.env.docker`, переменные окружения (JWT, DB, WebDAV). |
| C27 | Почему DotNetEnv? | Удобная загрузка `.env` при локальном запуске и в Docker. |
| C28 | Что в проекте Tests? | Консольный клиент для ручного прогона API-сценариев, не unit/integration suite. |
| C29 | Планируются ли автотесты backend? | Да: сначала unit домена, затем integration критичных сценариев. |
| C30 | Известные техдолги backend? | Refresh tokens, усиление хеширования паролей, единый error format, нейминг Album/Albom, SaveChanges в репозиториях. |

## Раздел F. Безопасность

| № | Вопрос | Краткий ответ |
|---|--------|---------------|
| F1 | Как защищён API? | JWT, роли, проверки владельца, HTTPS в production. |

| F8 | Валидация загрузок файлов? | Ограничение размера; проверка типов на уровне приложения. |
| F9 | CORS — зачем? | Разрешить запросы только с доверенного frontend origin. |
| F10 | Планируется ли CSP на frontend? | Да, если не чрезмерно усложняет — базовые security headers. |

| № | Вопрос | Краткий ответ |
|---|--------|---------------|

# Раздел Z. Два частых вопроса — по 3 варианта ответа каждый

## Z1. Почему проект первостепенно на английском, если мы в русскоязычной стране?

### Вариант ответа 1 (технический / индустриальный)
Интерфейс изначально разрабатывался на английском, потому что это стандарт де-факто в IT: англоязычные названия в коде, библиотеках (Next.js, Swagger, JWT), документации фреймворков и музыкальной нотации (chord names, Down/Up). Это упрощает сопровождение и соответствие принятым в отрасли конвенциям. Локализация на русский **запланирована** как отдельная приоритетная задача (RU/EN переключатель, язык по умолчанию — системный или EN).

### Вариант ответа 2 (продуктовый / аудитория)
Целевая аудитория — музыканты, для которых термины «chord», «pattern», «album» уже привычны независимо от языка интерфейса. Английский UI на этапе MVP позволил быстрее собрать работающий прототип и сфокусироваться на **предметной логике** (редактор песни, структура, аккорды), а не на переводе всех строк. Для пользователей из РФ предусмотрена полная русификация интерфейса.

### Вариант ответа 3 (учебный / этапность диплома)
Дипломный проект развивался итеративно: сначала — архитектура и ключевые сценарии на одном языке для единообразия тестирования и демо. Русский язык не исключён — он входит в roadmap (i18n обязателен по плану развития). На защите можно показать, что **контент песен** пользователь вводит на любом языке; локализация касается только оболочки приложения, а не творческого текста.

## Z2. Почему нет проверок на грамматические ошибки при создании песен?

### Вариант ответа 1 (границы задачи / scope диплома)
Предметная область проекта — **музыкальная структура** (сегменты, аккорды, паттерны, аудио), а не лингвистическая корректура текстов. Проверка орфографии и грамматики — отдельная NLP-задача (морфология, контекст, сленг в lyrics), выходящая за рамки ТЗ диплома. Валидация сосредоточена на обязательных полях, лимитах и целостности структуры песни.

### Вариант ответа 2 (техническая сложность)
Грамматическая проверка для песен сложнее обычного spell-check: рифмы, повторы, разговорная лексика, английские вставки в русском тексте дают ложные срабатывания. Потребовались бы внешние API (Yandex.Speller, LanguageTool) или ML-модели, мультиязычность и UX для «игнорировать предупреждение». Для MVP это неоправданно по соотношению **сложность/польза**; функцию можно добавить в будущих версиях как опциональную подсказку, не блокирующую сохранение.

### Вариант ответа 3 (свобода творчества пользователя)
Текст песни — художественный материал: намеренные ошибки, диалекты, сокращения и разговорные формы — норма. Жёсткая грамматическая валидация мешала бы авторам и давала бы некорректные замечания. Система проверяет **техническую корректность** (есть ли название, сегменты, привязки аккордов), а за литературным качеством текста отвечает сам пользователь — как в обычном текстовом редакторе.
